# V2 independent product-generation protocol

## A. Rehydrate and verify

1. Read the rehydration files and normalized transcript before making product-death or promotion
   decisions.
2. Inspect the 310-record registry and actual source code. Do not infer an interface from a title alone.
3. Run the packaged V2 tests and the source product's tests before modifying anything.
4. Preserve all source files as immutable inputs. Put new work in a new product directory.

## B. Find a synthesis

1. Search both directions: strength fills weakness, output satisfies input, and two mechanisms share an
   actionable state/decision boundary.
2. Ask whether the proposed product has standalone value, component value, or both.
3. Reject mere adjacency. A composition must change an objective, feasible set, posterior, controller,
   certificate, router, state representation, allocation, or observable decision.
4. Keep assumptions explicit: units, time scale, support, conservation, information state, intervention
   semantics and costs.
5. The ranked queue is a map, not a prison. Explore unranked pairs if code inspection reveals a stronger
   mechanism.

## C. Build

Every new product needs:

- executable source code;
- focused invariant/oracle tests;
- a mechanism-removing or strong comparator;
- a deterministic benchmark before stochastic expansion;
- explicit strength, weakness, working-region and failure-region fields;
- router, fallback or abstention behavior where uncertainty is material;
- separate standalone and component roles;
- exact parent IDs and evidence tiers;
- a `PRODUCT_RESULT.md`, `README.md`, benchmark script and machine-readable result.

Do not call a wrapper a new product merely because it has a new acronym. Demonstrate non-additive value.

## D. Interpret failure

Use the statement:

`candidate loses/ties comparator C on metric M in shell S using data D`.

Then diagnose one or more of implementation, calibration, shell mismatch, support violation, missing
state, bad comparator, insufficient sample, cost regime, time horizon, nonstationarity or a genuinely
narrow mechanism. Preserve the failed run. Repair or route it. Do not globally delete the product.

## E. Evidence axes

Report code correctness, mechanism evidence, transfer, operational decision value and deployment
maturity separately. Commercial upside is another axis. Original executable material and reconstructed
material retain different provenance even when both pass tests.

## F. Independence from the main lab

The independent lab may create its own `V2X###` IDs to avoid collision with main-lab `V2P###` IDs.
It must not rewrite the packaged registry in place. Its return package should include an append-only
proposal registry and exact patches or complete new directories so the main lab can inspect and merge
selectively.
